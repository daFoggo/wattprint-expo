# Benchmark baseline, 2026-10-25

Method follows `docs/superpowers/specs/2026-10-25-data-architecture-design.md` ("Benchmark method").
Everything labelled **measured** comes from the raw files in `docs/benchmarks/raw/`; everything labelled
**inferred** is reasoning on top of them and was not tested. All numbers are relative: x86_64 emulator, not a phone.

| Device | emulator-5554 only, AVD `Medium_Phone_API_37.0` (Android 17 / API 37, google_apis_playstore x86_64, 8 cores, 2048 MB RAM, 1080x2400, `hw.gpu.mode=auto`) |

(`stale=<ms>`, `delay=<ms>`, `prefetch=1`, see the appendix) used for the cache and list scenarios. Scenario 5 used the
debug dev build with Metro and throwaway render logging. All instrumentation was reverted: `git diff` of `src/` is empty.

## Commands

```
git checkout -b bench/results
npx expo run:android --variant release --no-bundler        # build A, then build B (instrumented)
bash scripts/bench/cold-start.sh 10 docs/benchmarks/raw/cold-start.csv
bash scripts/bench/list-bench.sh 5 docs/benchmarks/raw/list-bench.csv          # build B
bash scripts/bench/cache-bench.sh 5 docs/benchmarks/raw/cache-bench.csv        # build B
bash scripts/bench/resume-bench.sh 5 docs/benchmarks/raw/resume-bench.csv      # build B
pnpm android                                                # debug build + Metro
bash scripts/bench/rerender.sh 5 docs/benchmarks/raw/rerender-debounce300.csv debounce300
node scripts/bench/stats.js <csv> <groupColumns...>         # median/min/max
EXPO_ATLAS=true npx expo export --platform android --output-dir <dir>
```

Per-run flow: `am force-stop`, `logcat -c`, deep link `wattprint://...` via `am start -p com.dafoggo.wattprint.dev -a VIEW -d '<url>'`
(single-quoted for the device shell, otherwise `&` truncates the URL; this bit me once, see caveats).
`list-bench.sh` per sample: launch `wattprint://lab?prefetch=1` (prefetches quotes 100/500/1000 at start), wait 7 s, open
`wattprint://lab/bench?impl=<flash|flat>&n=<n>`, wait 5 s, `dumpsys gfxinfo reset`, 10x `input swipe 540 1800 540 300 80`
(0.3 s apart), `dumpsys gfxinfo`, `dumpsys meminfo`. Impl order alternates per run (odd runs flash first).
All 30 samples logged `cached=true` (so no network in the list numbers).

## What each `[BENCH]` line measures (read from the code)

- `home-ready`: `Date.now()` in the root layout `useEffect`, i.e. after the first tabs mounted, not after pixels.
- `http`: `ms` from just before `fetch` to the end of `response.text()` inside `lib/http.ts`; one line per attempt.
- `products-content`: mount of `ProductsScreen` to the first non-placeholder data in an effect; `fromCache=false` means a fetch ran.
- `bench-first-native-layout`: mount of `ListBenchScreen` to the first row's `onLayout` (native layout pass, not on-screen pixels).
- `detail-content` / `detail-real` (throwaway): mount of the detail screen to first data (placeholder or not) / first non-placeholder data.
- `render`, `screen-render`, `row-render` (throwaway, dev build): React Profiler commits of the list subtree, renders of `ProductsScreen`, renders of `ProductRow`.

## 2. FlashList vs FlatList (build B, release, prefetched, 5 runs per cell, measured)

QuoteRow is text only (no images). Frames come from `gfxinfo` over about 420 frames per sample. Values are median (min-max).

| n | impl | first native layout ms | janky % | p50 / p90 / p99 ms | PSS MB |
| --- | --- | --- | --- | --- | --- |
| 100 | FlashList | 18 (16-20) | 3.09 (2.75-4.91) | 17 / 18 / 19 (p99 18-29) | 121.1 (120.5-122.1) |
| 100 | FlatList | 11 (10-12) | 4.59 (4.15-5.33) | 17 / 18 / 19 (p99 19-32) | 128.1 (127.5-128.7) |
| 500 | FlashList | 21 (19-25) | 1.15 (0.49-2.91) | 17 / 18 / 19 (p99 19-34) | 128.1 (127.7-130.9) |
| 500 | FlatList | 10 (10-13) | 5.18 (4.75-5.75) | 17 / 18 / 19 (p99 19-29) | 169.2 (165.2-173.1) |
| 1000 | FlashList | 21 (18-24) | 1.15 (0.92-2.38) | 18 / 18 / 19 (p99 19-34) | 129.3 (128.2-129.8) |
| 1000 | FlatList | 11 (10-33) | 5.78 (5.21-6.47) | 17 / 18 / 21 (p99 19-34) | 168.2 (166.4-177.0) |

Reading:
- Janky %: FlashList lower at n=500 and n=1000 (ranges do not overlap). At n=100 the ranges overlap, so no difference can be claimed.
- Percentiles are at the 60 Hz frame floor (17-18 ms) for both; p99 ranges overlap in every cell: no difference.
- PSS: FlatList about +40 MB at 500 and 1000 (not overlapping); FlashList is flat from 500 to 1000. At 100 the gap is 7 MB.
- First layout: FlatList about 10 ms earlier at every size (ranges do not overlap, `Date.now` resolution is 1 ms). Real but imperceptible. The 33 ms FlatList run is one outlier.
- No order effect visible (values similar for first and second position).

## 1. Cache hit vs refetch (build B, release, fresh process per run, 5 runs, measured)

Config = `staleTime` (default 30000 vs forced 0) and dummyjson `delay` (0 or 1000 ms). Medians; ranges in raw CSV.

| Scenario | stale 30s, delay 0 | stale 0, delay 0 | stale 30s, delay 1000 | stale 0, delay 1000 |
| --- | --- | --- | --- | --- |
| List cold open: requests / time to content ms | 1 / 958 (926-2026) | 1 / 959 (942-1009) | 1 / 1943 (1928-2593) | 1 / 2145 (1956-2601) |
| Detail opened directly (no cached list): requests / ms to data | 1 / 696 (681-746) | 1 / 714 (695-1017) | 1 / 1930 (1912-1944) | 1 / 1932 (1898-2003) |
| Detail from cached list (placeholder): requests | 1 | 2 | 1 | 2 |
| same: ms to first content (placeholder) / ms to real data | 5 / 76 (63-81) | 5 / 81 (77-117) | 5 / 1309 (1274-1317) | 5 / 1293 (1271-1308) |
| Close and reopen the same detail: requests | 0 | 2 | 0 | 2 |
| same: ms to content (from cache) | 4 (3-4) | 4 (3-4) | 4 (3-4) | 4 (3-4) |

Return to the app after HOME (list open, `resume-bench.sh`, n=5):

| Config | requests after return |
| --- | --- |
| stale 30s, away 3 s | 0 in 5/5 |
| stale 30s, away 36 s | 1 in 4/5, 0 in 1/5 (one run did not refetch; not explained) |
| stale 0, away 3 s | 1 in 5/5 |

Reading:
- Within `staleTime`, reopening a screen costs 0 requests and paints from cache in about 4 ms. With `staleTime: 0` the same reopen paints from cache
  just as fast but always refetches (in the sample log the second request is the products list refetch, `raw/sample-logs.txt`; why the list refetches when
  the detail opens was not investigated).
- Placeholder from a cached list row gives content at about 5 ms, versus about 696 ms for a detail opened with nothing cached. This comparison is confounded: the
  direct-open run also includes the cold process and the first TLS connection (its request takes about 650 ms, later requests 75-90 ms). The placeholder benefit
  is large in the `delay=1000` rows (5 ms vs 1930 ms), where connection setup is not the explanation.
- `staleTime` has no effect on cold-open numbers (nothing is cached).
- Persistence was not measured (no persister exists in the repo). What is measured: after every `force-stop` the list needed 1 request and showed content at about 0.96 s, so the
  cache is memory-only today.

## 5. Re-render counts (dev build, Profiler, 5 runs each, measured)

Counts after the action, medians (min-max). `Fetches` = `http` lines. `typing` was done by `adb shell input text`.

| Action | debounce | fetches | screen renders | rows rendered | list commits |
| --- | --- | --- | --- | --- | --- |
| type "phone" in one `input text` | 300 ms (current) | 1 (1-1) | 5 (4-5) | 15 | 4 |
| same | 0 ms (temporary) | 2 (1-3) | 5 (4-6) | 15 | 4 |
| type "phone" one char every ~0.5 s | 300 ms | 5 | 13 (13-15) | 25 | 20 |
| same | 0 ms | 5 | 15 | 25 | 20 |
| pull-to-refresh, data unchanged | n/a | 1 | 2 | 0 | 6 |
| switch to Settings tab and back | n/a | 0 | 0 | 0 | 0 |

Reading:
- A refetch that returns identical data re-rendered 0 rows (measured). The 2 screen renders are fetch-status changes. Inferred: structural sharing keeps the `data` reference.
  The 6 list commits come from the Profiler wrapping FlashList (refresh indicator), not from rows.
- Debounce 300 ms saves fetches only when keystrokes are closer than 300 ms: fast input 1 vs 2 (range 1-3); at one key per 0.5 s it saves nothing (5 and 5). Inferred
  from these two points; real typing speed was not measured.
- Dev-build timings are not used anywhere. React Compiler status was not re-checked in this run.

## Caveats and what could not be concluded

- Emulator x86_64 on a desktop CPU: nothing here predicts phone frame times, memory, or cold start. The relative FlashList/FlatList ordering is plausible on
  device but unverified. The physical phone was never used.
- Network numbers come from dummyjson over the host connection; request latency is noisy (list cold open ranges up to 2.0-2.6 s in single runs).
- Rows are text only; FlashList vs FlatList with images (the product list) was not measured.
- The emulator died during cache-bench run 4 (config 0:1000). It was restarted headless (`-no-window`, GPU path may differ from the earlier windowed runs). Rows
  produced during the failure were discarded and re-run: cache-bench run 4 for `0:1000` and `30000:1000`, run 5 for all configs. The list/gfx numbers all came
  from the earlier windowed session.
- Bug found in my first cache script: the return-to-app intent was not resolvable, so the original `L_resume_*` columns are invalid. They are blanked in
  `cache-bench.csv` and replaced by `resume-bench.csv`.
- `am start -S -W` TotalTime is time to the first frame, not time to useful content; JS-ready is measured at the root layout effect.
- APK size is universal (4 ABIs); no base APK; the `.hbc` in the APK differs from the `expo export` file and the cause was not checked.
- Production-env build (`EXPO_PUBLIC_APP_ENV=production`, logs silenced and Lab tab hidden) was not built or measured.
- Atlas sizes are pre-Hermes JS bytes per package and only relative; zod at 0.94 MB suggests little tree shaking, not checked.

## Conclusions

Measured:
1. The cold list view needs one network round trip (about 0.96 s here) and the process is ready at about 0.67 s; every cold launch refetches.
2. Inside `staleTime` (30 s) a reopen is free (0 requests, about 4 ms); at `staleTime: 0` it is always a refetch, and opening a detail also refetched the list in this setup.
3. A cached-row placeholder shows the detail in about 5 ms regardless of network delay.
4. On this emulator FlashList had lower jank at 500 and 1000 rows and about 40 MB less PSS than FlatList; first layout was about 10 ms slower; frame percentiles were equal.
5. The lab adds about 187 KB (+3.2%) to the `.hbc`; FlashList is the largest part (about 233 KB of pre-Hermes JS).
6. Identical refetch data re-rendered 0 rows.

Inferred (not tested):
- Persisting the cache would replace the cold-start spinner with cached content, saving up to the network time (about 0.6-1.0 s here); hydration cost from MMKV was not measured.
- The FlashList advantage should hold on a device, probably larger on slow phones.

## Recommendations

- Keep the default `staleTime` at 30 s; set it per query when data changes faster (energy readings) or slower. Do not use 0 as a default: it doubles requests on navigation (measured).
- Keep the detail `placeholderData` from list rows.
- Persistence: the numbers support trying it for read-mostly lists and dashboards (cold start always pays one round trip). Decide after a short spike that measures
  MMKV hydration time and sets `maxAge`/buster; do not persist everything.
- Lists: use FlashList for lists that can pass a few hundred rows (jank and memory gain measured); FlatList is fine up to about 100 rows. Re-measure with image rows on a real
  device before locking it.
- Keep debounce at 300 ms for search; its benefit is real only for fast typists.

## Appendix: throwaway instrumentation (reverted)

`raw/instrumentation.patch` holds the original edits: `staleTime: () => benchFlags.stale` in `query-client.ts`, `withDelay()` around the four dummyjson paths in
`features/lab/api.ts`, `detail-content`/`detail-real` logs in the detail screen, prefetch of quotes 100/500/1000 in the root layout when `prefetch=1`. The final
`src/lib/bench-flags.ts` (since removed) was lazy (read at first use, because the first read at import time got a truncated URL; the real cause was the unquoted `&` in my adb command):

```ts
import * as Linking from 'expo-linking';
let loaded = false;
const state = { stale: 30_000, delay: 0, prefetch: false };
function load() {
  if (loaded) return state;
  const url = Linking.getLinkingURL();
  if (url) {
    loaded = true;
    const p = Linking.parse(url).queryParams ?? {};
    if (typeof p.stale === 'string') state.stale = Number(p.stale);
    if (typeof p.delay === 'string') state.delay = Number(p.delay);
    if (p.prefetch === '1') state.prefetch = true;
  }
  return state;
}
export const benchFlags = { get stale() { return load().stale; }, get delay() { return load().delay; }, get prefetch() { return load().prefetch; } };
export const withDelay = (path: string) =>
  benchFlags.delay > 0 ? `${path}${path.includes('?') ? '&' : '?'}delay=${benchFlags.delay}` : path;
```

Scenario 5 edits (dev build): log every Profiler commit in `render-count.tsx`, a `row-render` log in `ProductRow`, a `screen-render` log in `ProductsScreen`, and
`SEARCH_DEBOUNCE_MS = 0` for the no-debounce rows.
